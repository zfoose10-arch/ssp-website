# Build lane

A workflow skill: how this house runs a gated build session. Minted 2026-09-05 from the four sessions of that day (hooks, sandbox posture, data wall, the Judge), the learning crossing added the same evening, and pinned to the doctrine it mirrors: the Change Protocol v1.4 (the second lap and the twelve checks, 2026-09-22), The Judge v2.2 (the second lap and the twelve checks, 2026-09-22), Spec Contract v1 (2026-09-11), Rules Moved to Hooks v2.2 (the three hook classes, the managed settings placement since 2026-09-14, and the paste wrapper strip, 2026-09-21), Build Lane v1.6 (the second lap in phase 8 and the twelve checks, 2026-09-22), the three lines beside the halt class and the second lap in the AIOP Build Doctrine v1.13, and the hard rules in 00 Identity/soul.md. Reverify the pins at each bump; a mirror drifts silently.

## The delta prompt

A build prompt names five things and nothing else: the change; the upgrade or ruling behind it; this build's own constraints (surface, client scope, time box, what stops the session); the proof plan; the doctrine homes. Everything below is supplied.

## Phases, each with its exit condition

1. **Gate.** Run `~/scripts/prebuild_gate.sh <surface>` first. Explain every bypass line it surfaces or say unexplained. Judge the dirty tree: the nightly's staging files and today's note accumulate by design and are left alone. Name the next scheduled leg. On GATE HOLD write `~/Downloads/gate-<surface>-<name>-<date>.md` and stop. Then read this session's owner queue, `_system/queues/<slug>.md` for the owner the delta names or the surface implies by the README's keyword table (governance-repair for lane, gate, hook, ledger, skill, report, and proof work; judge; page-session; website; oracle; nightly), and start with its filed list: the proposal names which entries this build takes and which stay, and the report phase appends ` - taken <date>: <report name>` to each taken entry. Exit: GATE CLEAR recorded and the queue read.
2. **Recon and design.** Read what the delta names plus the doctrine this skill pins, and read current tool behavior by fetching the docs, never from memory, saving the excerpt and the version line to a dated file beside the proposal. Write `~/Downloads/<name>-proposal-<date>.md` in the Zane Brief shape and in the planning shape: the outcome, the constraints, three approaches with their trade-offs, one committed recommendation, and then the spec's first draft, and stop there; procedure is written only where a hard rule dictates a step. The spec is the build's contract, per 07 Knowledge/Spec Contract.md: durable lines, what must hold when the build is done, each falsifiable and each naming its proof, numbered D1 onward and marked apart from disposable lines, how we think we will get there; a baseline read from disk before any work starts; and a finish condition. The Judge verifies against the durable lines and never against the plan, so a durable line that cannot be proven is not written. Print a five line lead. Stop until Zane types confirm. Nothing is written outside Downloads before confirm. Exit: confirm received.
3. **Build with proof.** Build. Every proof run appends one line to `~/scripts/_state/proof_runs.log`: `<YYYY-MM-DD HH:MM:SS> <script or cell name> <closing count line or verdict>`. A failing cell is fixed only under the scoped stop clause: the defect is in code this session or its same day predecessor shipped, the fix is proven again through the full matrix, and the deviation is flagged in the report; a defect in standing machinery, a fix that cannot be reproven in full, or anything touching an authority stops the session. Inside that clause the fix walks the ladder: reproduce the failure before fixing it, and a defect that cannot be reproduced is investigated, not patched; no fix raises a limit or a retry count without a named cause; after a second failed fix on the same defect, the tried list is written to a file and handed to a fresh subagent with the instruction not to repeat it; after that, a rewrite plan with a reference implementation named, never a third patch; a third patch on the same defect halts to the Desk under For review. A mechanical check beats a model call wherever one can do the job. Exit: every cited proof green on its last run and logged.
4. **Doctrine homes.** Mint or amend what the delta names: the knowledge note, the doctrine rule, the hook or skill. Walk both build lane routers when the Build Doctrine moves. Exit: every named home exists and cites the version.
5. **Change Protocol.** Claim the ordinal through `~/scripts/ledger_ordinal.sh claim` before any ledger write. Add or amend rows; walk every dependent by reading and sync or flag it with today's date; retrue version cells in the same pass. Insert the history entry above the previous top entry, keeping that entry's marker in full, and predict the gate's top three ordinals before running it. Commit the ordinal after the entry. Exit: the gate's 4b and 4c agree and the entry names every row it touched.
6. **Scoped commits.** One commit per repo touched, by path, naming the ordinal, staging files untouched, attribution lines as the session requires. The report will name every file each commit changed, because the Judge matches by name. Exit: every touched repo committed.
7. **Report, then the mechanical preflight.** Write `~/Downloads/<name>-session-<date>.md`: where he stands, one thing to know, next, as three short paragraphs; then a line; then Detail (what runs where), a Spec section, Deviations flagged, Owed with an owner or trigger on every line, a BOUNDARY CONFIRMATION line naming every file written outside the vault and the hub, and the machine block as the report's last lines. The Spec section is the heading Spec carrying every durable line of the proposal's spec, one per line as `- D<n> | <the line> | met, unmet, or not checkable | <what shows it>`, then a line beginning Baseline and a line beginning Finish; a met line names the proof that shows it, an unmet line is written as unmet and never argued past, and a not checkable line's last field reads `checkable by:` and the artifact that would have made it checkable. The Judge's eleventh check reads that section and an unmet line, a bare not checkable, or a missing section fails the report whatever the other eleven checks say. Every item the session holds appears; the wording compresses, never the list. The report describes the learning crossing as owed, never as done, because the crossing runs after the Judge's verdict and its queue entries and For review lines are its record; that Owed line names this session's phase 8 as its owner and the verdict file as its trigger. The machine block is where the Judge's mechanical checks read every fact, and never the prose: seven lines under a `MACHINE BLOCK` line, keys fixed, `ordinal:` the ordinal claimed or none; `commits:` every commit as `<repo> <hash> <path>, <path>`, semicolons between commits, repo names vault, scripts, hub, website, client, sidecar, paths as git show prints them; `scripts:` every proof script run, by path; `proof lines:` every proof log line this session wrote, verbatim, semicolons between; `files:` every file written or changed, by path; `versions:` every doctrine version moved as `<doctrine> v<X.Y>`, or none; `verdict: pending, written by judge.sh` as the last line of the report. Then the preflight: run `~/scripts/judge_checks.py <report> <surface> ~/Downloads/judge-preflight-evidence-<name>-session-<date>.<YYYYMMDD-HHMMSS>.md`, answer any FAIL by correcting the block or the fact it reflects, and name the preflight and its evidence file in the report; the preflight logs its own proof line. Exit: the report stands alone and the preflight reads twelve of twelve.
8. **Judge, then the learning crossing.** Run `~/scripts/judge.sh <report> <surface>`, which reruns the gate, runs the twelve checks into an evidence file, reads the report cold through two or three reviewer layers, the mechanical reader, the domain reader for the surface, and the client's champion where the report carries a CLIENT SCOPE line, each a fresh print run writing its observations, its spec walk, and its findings to `~/Downloads/judge-layer-<layer>-<report>.<stamp>.md`, and then runs the composer, which walks every durable line of the report's Spec section against the artifacts and the layers and writes the verdict with its Spec table; every file is kept under a run stamped name and the report's verdict line is pointed at the latest; take the verdict path from the report's last line. The Judge's target is the Spec section and the artifacts, never the proposal. A FAIL on a session that touched a governed authority or a client repo re enters the fix ladder and is re judged to PASS before the closing gate: the FAIL is answered by fixing what it found, never by rewording the line it found it on, and the report says what each lap fixed. Files moved between laps are named in the report's block, and every prior verdict is kept under its stamp. Where a PASS is unreachable because of a machine state Zane has ruled, the report says so and names the check. Then run `~/scripts/learning_crossing.py <report> --verdict <verdict>`, which extracts candidate lessons from the report's flagged deviations and the verdict's findings, writes each lesson that names an owner and a trigger to that owner's queue under `_system/queues/` (the same lesson raised twice collapsing into one entry), prints the rest under For the night, and logs the counts; read those, drop any whose fix already lives in a home, fold duplicates into one lesson, and write each open one as one plain register line under today's For review with a judged home, for the night's triage and Zane's ruling. The report's crossing record names the counts, queued, collapsed, and left for the night. Nothing is applied to a home by the session. Exit: the verdict file exists and the report's last line names it, the owned lessons are in their queues, and the unowned are under For review.
9. **Closing gate.** Run `~/scripts/prebuild_gate.sh <surface>` as the last act. The terminal prints only the verdict line and the report path. Exit: GATE CLEAR.

## Standing constraints

- The five hooks are live: obey them, route around a refusal, never disable one.
- Three lines beside the halt class, from the AIOP Build Doctrine v1.13: a model's refusal of work outside the ruled bounds is a halt and never a rung on the ladder; a failed credential halts and is never worked around; an unattended run is scoped to the one to three hour reliability band, and anything longer is split at a checkpoint.
- The prompt ends with the terminal marker line; a prompt without it is truncated and the session halts.
- Any output over 2,500 characters goes to a dated file under Downloads with a short terminal lead; the chat message is the pointer, not the deliverable.
- A CLIENT SCOPE line whenever a client repo is touched; that client's document home is never read unless the delta says so; every proof on fabricated fixtures.
- Nothing is deleted; duplicates merge into a survivor marked for Zane's hand.
- Identity files are edited only under the token Zane writes by hand, after the proposed change is shown.
- No em dashes and no hyphen joining clauses, in any file and in every line a script prints.
- Working directory resets between shell calls: absolute paths always.
- One prompt at a time; a time box in the prompt is absolute: stop clean, commit nothing half done, and write the report saying where it stopped and what a resume prompt needs.

## Resume

A stopped session's report names the phase it stopped in and the artifacts that exist. The resume prompt names that report and says continue; the skill picks up at the named phase, reruns the gate first, and claims no second ordinal when one is already claimed and uncommitted for the session.
